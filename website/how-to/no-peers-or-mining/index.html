How-to / Troubleshooting

Fix no peers or mining waiting

Work from the node’s own status in a safe order. Most waiting states protect canonical mining and should be diagnosed—not bypassed.

Troubleshooting · About 10 minutes
01Observe02Peers03Mining04Logs

01 / Observe

Read the app before changing anything

Open Overview, Blockchain, Network, and Mining. Record what each page reports.

  • Is the node process Running or Stopped?
  • Is local status online?
  • Is local height increasing?
  • How many direct peers are connected?
  • What exact Mining status and detail are shown?
  • Does the Network page show Clearnet or Tor-only?
Do not use Task Manager activity as the verdict. A process can consume CPU and memory while still opening chain state, synchronizing, or safely waiting for peer confirmation.

02 / Peers

Restore healthy peer connectivity

  1. Allow initial discovery time

    After a fresh start or transport change, wait for the Network page to populate before restarting again.

  2. Confirm the intended transport

    Tor-only preparation must succeed before Tor peers can connect. On Clearnet, outbound peers work even when no inbound mapping is available.

  3. Check ordinary internet access

    Resolve captive portals, disconnected VPNs, restrictive security software, or a network that blocks outbound connections.

  4. Check Windows time

    Enable automatic date, time, and time-zone synchronization. Excessive clock drift blocks safe mining and can disrupt peer agreement.

  5. Review the firewall scope

    Inbound TCP 8333 is optional and should be limited to the signed node executable on Private or Domain networks. Never expose RPC 8334, the local wallet, or the local explorer.

Outbound-only is a valid operating state. If direct peers are connected and the chain advances, the absence of inbound peers is not a failure.

03 / Mining

Interpret the waiting state

Synchronizing

Wait for the Blockchain page to show Synchronized.

Waiting for anchor

No configured network anchor is connected. Restore peer connectivity and wait.

Clock drift

Correct the Windows clock and allow peer time checks to recover.

Genesis mismatch

Connected peers do not match this build’s genesis. Confirm the official current client and intended network; do not force acceptance.

Waiting for peer tip

Fresh canonical peer-tip confirmation is required.

Below peer floor

The configured peer confidence floor is not currently satisfied.

Propagation

The current tip is waiting for acknowledgement before new work is admitted.

Reorg rebuild

Derived chain state is being rebuilt safely. Let it finish.

Work admission

The node is waiting for safe canonical work admission.

Mining error

Open Logs and use the exact node-reported error for the next step.

Never weaken admission checks to make “Hashing” appear. Mining against an unverified or stale tip wastes work and can create orphaned blocks.

04 / Logs

Collect useful diagnostics

  1. Open Logs

    Read the newest local node output around the time the status changed.

  2. Use Copy diagnostics

    Capture version, node state, height, peers, sync mode, transport, and mining state together.

  3. Open the log folder when needed

    Use Open log folder to inspect the full local record. Review copied text before sharing because it can contain operational metadata.

  4. Restart once, cleanly

    If the app reports a transient startup error, stop the node, wait for it to exit, and start it once. Avoid repeated rapid restarts.

Keep identity files out of diagnostics. No support request needs miner.key, a .veld-keys file, its passphrase, or a private key.

Actions to avoid

  • Do not delete veld-data as a first troubleshooting step.
  • Do not replace chain state with files from another person.
  • Do not open RPC or local app ports to the internet.
  • Do not disable release signature checks.
  • Do not remove the mining identity unless a verified backup exists.
